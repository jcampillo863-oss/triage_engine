Exact trust boundary:
- Trusted authentication service code resolves protected credentials to `marketplace:producer:v1` with `PRODUCE_WORK`, or `marketplace:validator:v1` with `VALIDATE_WORK`.
- Configure independent cryptographically generated secrets through `MARKETPLACE_PRODUCER_SECRET` and `MARKETPLACE_VALIDATOR_SECRET`. Use URL-safe base64 encodings of at least 32 random bytes (for example, generated by `secrets.token_urlsafe(32)`); canonical encoding/length and separation are checked, while entropy must come from the secure generator. Missing, malformed or equal configuration fails closed. Both supplied-credential comparisons use `hmac.compare_digest` without short-circuiting. Configuration is read per authentication, so rotation does not rely on a process cache.
- Credentials exist only in protected process configuration and transient authentication arguments. No token, hash, fingerprint or credential-bearing principal handle is persisted/returned/logged. Responses contain canonical IDs and operation/decision identifiers. Operations reject configured credential strings in work data rather than storing them.
- Production `create_delivery(..., producer_credential=...)` does not accept a producer assertion. `record_work_evidence(...)` authenticates producer capability and derives task/commit from the immutable production delivery; the producer reports explicit observations, never validation decisions.
- `validate_work(..., validator_credential=..., work_delivery_id=..., evidence_id=...)` authenticates validator capability, accepts no validator/result/accepted assertion, reads the stored evidence matching that delivery, and uses the existing local evaluator. It writes the exact validation result and canonical technical decision. Missing tests remain inconclusive; failures cannot become accepted decisions. Wrong task/commit/environment/provenance fails closed.
- Producer credentials cannot invoke validation; validator credentials cannot produce deliveries/evidence. Authentication exposes neither GitHub acceptance nor financial capability. Eligibility and financial checks remain separate and unchanged.
- The Python service process, its code/configuration and exclusive DB access are trusted. These APIs are not a sandbox against code executing inside that process or an actor with direct SQLite write access. Do not distribute the authentication service's environment or DB access to untrusted workers. Request/exception tooling must not capture credential arguments or local variables. No OAuth, JWT, user accounts, IAM system or public server was added.

Authority audits use logger `marketplace.authority`, emitting only principal ID, capability, operation, outcome and UTC timestamp. Categories and principal IDs are sanitized; no caller body, signature or exception text is logged. Configure INFO-level persistent collection and restricted access in the trusted service before deployment. Technical acceptance remains separate from whether an authority operation successfully completed.
